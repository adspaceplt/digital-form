# ADspace Digital Portal — working rules

@DESIGN.md
@STANDARD.md

Static site, vanilla JS, no build step, served by GitHub Pages at
digital.adspace.me (CNAME in the repo). Pages: `admin/` (console),
`creators/` (client-facing creator selection), `review/` (client-facing
content review). Supabase behind `js/api.js`; schema in
`supabase/schema.sql` (re-runnable; the user runs it by hand in the SQL
editor, and must be told when). A change confined to one function or one
column ships instead as a dated file in `supabase/migrations/`, narrowly
scoped and safe to run twice, so a live database is not put through fifteen
unrelated data migrations to replace one function body.

The design system, the components, the laws and the copy rules are in
`DESIGN.md`. The general engineering and design standard, the working method
and the completion gate are in `STANDARD.md`, whose Project Memory records the
three places this portal deliberately departs from it (the spacing scale, the
14px body, and the 1280/390 viewport matrix). Both are imported above. Read all
three before any change; where they disagree, `STANDARD.md` §2 settles it and
this portal's documented behaviour wins.

### Non-negotiable validation before "done"

Nothing is pushed until every one of these has run on the final code:

1. `node --check` on every changed `js/*.js`.
2. Local server: `setsid nohup npx --yes http-server -p 8899 -s . >/dev/null 2>&1 &` from the repo root (it dies between turns; restart on `ERR_CONNECTION_REFUSED`).
3. The full behavioural sweep, every suite green (`0 FAIL`, no page errors):
   `for s in run camp client cprod bar newbadge prod qr regress backup keyin state race chrome crm sgd team portal; do node tests/$s.js tests; done`
3a. **For any change to a policy, a grant or a security definer function: `node tests/rls.js tests` → `rls: ok`.** It builds the real policy block on a throwaway Postgres and asks the same questions as six principals: an admin, Marketing, Sales, a client at one company, a client at another, and an anonymous visitor. It also proves the hole first, so the suite fails if the fix stops being a fix. Nothing in the browser suites can test a policy: `stub2.js` has no RLS at all.
3b. **For any change to `supabase/schema.sql`, including a seed or a function: `node tests/sql.js tests` → `sql: ok`.** It now covers the stage clock, the team sweep and repair, the overlap guard, the rate card seed, **and the whole creator delivery path** (a code is issued, an upload is allowed, a file is recorded, several files land on one booking, submitting moves the step and keeps the caption, a submitted file cannot be pulled back, an invalid code reaches nothing). It starts a throwaway Postgres 16 cluster and runs the real thing. Every other suite drives a browser against `stub2.js`, so a trigger written in PL/pgSQL was the one part of the portal nothing checked, and that is exactly where the stage clock broke: the trigger forced the old values back on every update, silently discarding the migration's own backfill, and all eighteen suites stayed green. A stand-in cannot catch a bug in SQL it does not run. It prints `SKIP` loudly where Postgres is missing rather than passing quietly.
4. `node tests/uxaudit.js tests` → must print `uxaudit: ok`.
